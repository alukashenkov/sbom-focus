# Syft SBOM Dependency Graph Insights

When analyzing container SBOMs generated by tools like [Syft](https://github.com/anchore/syft), the dependency graph (represented in the CycloneDX `<dependencies>` array) often exhibits a significant discrepancy in completeness between different ecosystems.

## OS Packages vs. Application Packages

### OS Packages (deb, rpm, apk)

Syft is highly effective at reconstructing dependency trees for operating system-level packages. This is because OS package managers (like `apt` or `yum`) maintain explicit, structured databases of dependencies on the filesystem (e.g., `/var/lib/dpkg/status`). Syft can reliably parse these databases to build comprehensive, root-to-leaf dependency graphs for the base OS layer.

### Application Packages (Python/pip, Node/npm, etc.)

There is a catch when dealing with application-level dependencies within container images. For ecosystems like Python's `pip` packages (e.g., `requests` or `flask`), Syft's cataloger usually doesn't reconstruct the dependency graph.

Instead of dynamically resolving build-time lockfiles (like `Pipfile.lock`, `poetry.lock`, or `requirements.txt`), Syft primarily relies on scraping installed metadata files (such as `.dist-info/METADATA` directories) discovered statically on the container's filesystem. Because these localized metadata footprints often lack the full structural context of the original build environment, application packages frequently appear in the SBOM as isolated components with no declared dependencies.

## Implications for Analysis

If you are writing scripts to analyze SBOMs or perform vulnerability reachability analysis:

1. **Expect disjointed graphs:** Do not assume the `<dependencies>` array contains edges connecting your application code to its transitive dependencies.
2. **Ecosystem-specific logic:** Your analysis scripts may find deep dependency trees for the `deb` layer, but mostly "flat" lists of isolated packages for the `python` layer.
3. **Tool chaining:** To get complete application dependency graphs, you often need to generate the SBOM at the *source code* or *build* level (using language-specific plugins) rather than scanning the final compiled container image.
